# 単体テスト

機能ができたら、その機能の関数ごとに単体テストを書いて実行し、テストケースと実行結果をこのフォルダに残す。
Claude Code を使っているときは、`/unit-test` と入力するとこの手順で進めてくれる
（手順の本体は [.claude/skills/unit-test/SKILL.md](../.claude/skills/unit-test/SKILL.md)）。

## フォルダの形

```
tests/
  README.md              … このファイル（ルール）
  _template/cases.md     … テストケースの一覧のひな形
  <機能名>/
    cases.md             … テストケースの一覧（何を確かめるか）
    results/
      2026-11-18_153000.md … 実行結果（npm run test:report が作る。手で書かない）

frontend/src/**/xxx.test.ts(x) … テストのコード（テストする関数のファイルの隣に置く）
backend/src/**/xxx.test.ts
```

- `<機能名>` はキャメルケースで書く（例: `borrowBook`、`returnLoan`、`formatDate`）。
- 1つの機能に、テストする関数が複数あってよい。cases.md の中で関数ごとに表を分ける。
- 実行結果は Git にコミットして、PR に含める。レビューする人は、結果のファイルでテストしたことを確認する。

## 手順

1. **テストケースを書く**: `tests/_template/cases.md` を `tests/<機能名>/cases.md` にコピーし、関数ごとに確かめることを書く。
2. **テストのコードを書く**: テストする関数の隣に `xxx.test.ts` を作る。`it()` の名前は、cases.md の ID で始める。
   ```ts
   it('FD-01: UTC の日時を、日本時間の「YYYY年M月D日」にする', () => { ... });
   ```
3. **実行して結果を残す**:
   ```sh
   npm run test:report -- <機能名> <テストファイル> [<テストファイル> ...]
   # 例
   npm run test:report -- formatDate frontend/src/utils/formatDate.test.ts
   ```
   `tests/<機能名>/results/` に実行結果のファイルができる。
4. **結果を確かめる**: 判定が「❌ 不合格」なら、直してから実行し直す。合格した結果のファイルをコミットする。

ふだんの確認だけなら `npm test`（全部のテスト）や `npm run test:watch`（保存するたびに実行）でもよい。この2つは結果のファイルを作らない。

## テストケースの ID

- 形は `<英大文字の略号>-<2桁の番号>`（例: `FD-01`、`BB-03`）。略号は機能ごとに決めて、cases.md の先頭に書く。
- `npm run test:report` は、cases.md の表にある ID と、実行したテストの名前の ID を突き合わせる。
  - cases.md にあるのにテストがない ID は「⚠ 未実行」として結果に出し、不合格にする。
  - テストにあるのに cases.md にない ID は「注意」として結果に出す。
- 一度使った ID は、ケースを消しても別のケースに使い回さない。

## テストケースの選び方

関数ごとに、少なくとも次の観点を考える。当てはまらない観点は書かなくてよい。

| 観点 | 例                                                                   |
| ---- | -------------------------------------------------------------------- |
| 正常 | ふつうの入力で、期待どおりの値を返す                                 |
| 境界 | 0・空の文字・最大の長さ・日付の変わり目など、ぎりぎりの値            |
| 異常 | 形の正しくない入力、存在しない ID などで、決めたとおりのエラーになる |
| 状態 | 貸出中／返却済みなど、データの状態で結果が変わるとき、それぞれの状態 |

## 書き方の決まり

- テストは、ほかのテストの結果や実行する順番に頼らない。
- 本物の DB（`backend/data/app.db`）や、起動中のサーバーを使わない。テスト中は `vitest.config.ts` で
  環境変数 `DB_PATH=:memory:` を設定しているので、`backend/src/db.ts` を読み込んでもメモリ上の使い捨ての
  DB が使われる。この設定は消さない。
- 日付・時刻はタイムゾーンを日本時間に固定している（`vitest.config.ts`）。いまの時刻に頼るテストは
  `vi.useFakeTimers()` と `vi.setSystemTime()` で時刻を決める。
- 画面の部品（React）をテストするときは、テストファイルの先頭に `// @vitest-environment jsdom` と書く
  （`jsdom` と `@testing-library/react` を、最初に使う人がインストールする）。
- バックエンドの処理は、いまは API（`backend/src/index.ts`）の中に直接書かれている。関数ごとにテストする
  ときは、処理を関数に分けて別のファイルに移し、その関数をテストする。
