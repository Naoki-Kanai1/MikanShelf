# 単体テスト

MikanShelf の単体テストの手順。ルールの本体は [tests/README.md](../../../tests/README.md)。
始める前に必ず読み、そこに書かれた決まり（フォルダの形、ID の形、書き方）に従う。

## 0. 準備

テストに使うライブラリ（Vitest など）は、pull しただけでは入らない。次のどれかに当てはまるときは、
テストを書き始める前に、リポジトリのルートで `npm install` を実行する。

- `node_modules/vitest` のフォルダがない
- pull した直後などで、`package.json` や `package-lock.json` が変わっている
- テストを実行して `Cannot find module` や `vitest/package.json` が見つからないというエラーが出た（`npm install` してからやり直す）

## 1. テストする関数を決める

- ユーザーが機能や関数を指定していれば、それを使う。
- 指定がなければ、`git diff main...HEAD --stat` とコミットしていない変更から、今回作った・変えた関数を探す。
- 見つけた関数と、`<機能名>`（キャメルケース。既に `tests/` にあればその名前）を一覧にしてユーザーに見せ、
  これでよいか確認してから次に進む。
- 処理が API のハンドラーの中に直接書かれていて関数として呼べないときは、**勝手に作り替えない**。
  どの処理をどのファイルの関数に分けるかを提案し、了承を得てから分ける。

## 2. テストケースを書く

- `tests/<機能名>/cases.md` がなければ `tests/_template/cases.md` をコピーして作る。あれば追記する。
- 関数のコードを読み、tests/README.md の「テストケースの選び方」の観点（正常・境界・異常・状態）で
  ケースを洗い出す。仕様が読み取れないところ（エラーのときに何を返すべきかなど）は推測で決めずに質問する。
- 既にある ID は変えない。新しいケースは、続きの番号を付ける。

## 3. テストのコードを書く

- テストする関数のファイルの隣に `xxx.test.ts`（画面の部品なら `xxx.test.tsx`）を作る。
- `it()` の名前は、cases.md の ID で始め、そのあとにケースの内容を書く（例: `'FD-01: …'`）。
- cases.md の全部のケースに、テストを1つずつ書く。
- 本物の DB や起動中のサーバーは使わない。

## 4. 実行して結果を残す

```sh
npm run test:report -- <機能名> <テストファイル> [<テストファイル> ...]
```

- 実行結果は `tests/<機能名>/results/<日付>_<時刻>.md` に自動でできる。**結果のファイルを手で書いたり直したりしない。**
- 不合格のとき:
  - テストのコードの誤りなら、直して実行し直す。
  - 製品のコードの不具合と思われるときは、**製品のコードを直す前に**、どのケースがなぜ失敗したかをユーザーに報告し、
    直すかどうかを決めてもらう。テストを期待値に合わせて書き換えて合格させてはいけない。
- 途中の失敗した実行の結果ファイルは、残してよい（直した経過が分かる）。不要とユーザーが言えば消す。

## 5. 報告する

次をユーザーに報告する。コミットは、ユーザーの了承を得てから行う。

- テストした関数と、ケースの数（観点ごと）
- 判定（合格／不合格）と、結果のファイルのパス
- 失敗したケースがあれば、その内容と原因の見立て
- 見つけた不具合や、テストしにくかった処理（関数に分けたほうがよいものなど）
